# Parte I: Poniendo el modelo de dominio en funcionamiento

## Modelo

Un modelo representa algún aspecto de la realidad o una idea de interes.

Una modelo es una interpretación de la realidad que abstrae los aspectos mas relevantes para resolver un problema e ignora los detalles superfluos.

Todo programa de software  se relaciona con alguna actividad o interes del usuario. *El ambito temático al que el usuario aplica el program es el dominio de software*

- El ambito de un programa de reservas de vuelos implica que personas reales suban a aviones reales

Algunos dominios son intangibles:

- El dominio de un programa de contabilidad es el dinero y las finanzas

Los ámbitos del software suelen tener poco que ver con los ordenadores aunque hay excepciones. 

- El dominio de un sistema de control de código fuente es el desarrollo de software en si

La amplitud de conocimientos requerida para que un equipo de desarrollo de software pueda aportar valor a un proyecto puede ser abrumadora. El volumen y la complejidad pueden ser intimidantes. Los modelos son herramientas para gestionar la sobrecarga. Un modelo es una forma de conocimiento selectiva simplificada y conscientemente estructurada. Un modelo adecuado da sentido a la información y la centra en un programa.

El modelado de dominio no consiste en crear un modelo realista. Es mas bien como el cine: Representar la realidad de forma aproximada con un proposito especifico

## Útilidad de un modelo en el diseño orientado al dominio

Tres usos básicos determinan la elección de un modelo:

- El modelo y el núcleo del diseño se influyen mutuamente. La estrecha relación entre el modelo y su implementación es lo que hace que el modelo sea relevante y garantiza que el analisis realizado en él se aplique al producto final. Esta vinculación facilita el mantenimiento y el desarrollo continuo, ya que el código puede interpretarse en función de la comprensión del modelo (Capitulo 3).
- El modelo es la columna vertebral de un lenguaje usado por todos los miembros del equipo, ya que permite a los desarrolladores y usuarios no técnicos comunicar sobre el programa de manera clara y consistente (Capítulo 2).
- El modelo es conocimiento destilado. Es la forma acordada por el equipo para estructurar el conocimiento del dominio y distinguir los elementos de mayor interés. Un modelo refleja cómo elegimos abordar el dominio al seleccionar términos, desglosar conceptos y relacionarlos. El lenguaje compartido permite que desarrolladores y expertos del dominio colaboren eficazmente al organizar la información en este formato. La vinculación entre el modelo y la implementación permite que la experiencia con las primeras versiones del software se utilice como retroalimentación en el proceso de modelado. (Capítulo 1).

## El corazón del Software

La complejidada de negocio inherente al software debe abordarse directamente. De lo contrario corre el riesgo de volverse irrelevante. 

Los lideres de un equipo que comprenden la importancia del dominio pueden reconducir su proyecto de software cuando el desarrollo de un modelo que refleja una comprensión profunda se pierde en el caso

En el libro demostrará que el desarrollo de dominios ofrece oportunidades para cultivar habilidades de diseño muy sofisticadas. De hecho, en muchas disciplinas cientificas, la complejidad es de los temas mas apasionantes de la actualidad, ya que los investigadores intentan abordar la naturaleza caótica del mundo real. Un desarrollador se enfrenta a la misma peresectiva al trabajar con un dominio complejo que nunca ha sido formalizado. Crear un modelo claro que simplifique esa complejidad resulta estimulante.

Existen métodos de pensamiento sistemático que los desarrolladores pueden emplear para obtener información valiosa y crear modelos eficaces.

Hay técnicas de diseño que pueden poner orden en una aplicación compleja. Cultivar estas habilidades hace que un desarrollador sea mucho mas valioso.
