La arquitectura en el desarrollo de software 

Las nociones de diseño controlado únicamente por pruebas y el código, propias de finales de la década de 1990, ya no son válidas

Pero incluso en la industria automovilística, gran parte del trabajo no radica en la
fabricación sino en el mantenimiento, o más bien en cómo evitarlo.

En el software el 80% de lo que hacemos se denomina cuantitativamente mantenimiento, el acto de reparar. En lugar de optar por la típica costumbre occidental de crear software de calidad, debemos pensar como reparadores o mecánicos

**TPM (Total productive maintenance).-** Este enfoque de calidad aparecio en 1951, se centra en el mantenimiento no en la producción

Uno de los principios del TPM es el conjunto de principios denominados 5S

- ***Seiri u organización.-*** Saber donde están las cosas
- ***Sieton u sistematización.-*** Un sitio para cada cosa y cada cosa en un sitio.
- ***Seiso o limpieza.-*** Mantenga limpio el lugar de trabajo.
- ***Seiketsu o estandarización.-*** El grupo decide como mantener limpio el lugar de trabajo.
- ***Shutsuke o disciplina.-*** Disciplinado en la aplicación de las prácticas

***En el código debemos refactorizar sin compasión*** 

Fred Brooks nos dice que el software se debería rehacer cada siete años, tendríamos que actualizar este plazo a semanas, días e incluso horas

Debe bautizar a una variable con el mismo cuidado como si fuera su primogénito

La calidad es el resultado de un millón de acciones cuidadosas

La única medida de calidad por minuto est WTF's / minute

### ¿Cómo asegurarnos de que abrimos la puerta correcta cuando las cosas se ponen feas?

- La, respuesta es la maestría, la maestría se consigue de dos formas: conocimiento y trabajo

- Aprender a crear código limpio es complicado. Requiere algo mas que conocer principios y patrones. Tiene que sudar. Debe practicarlo y fallar

### Hágase el código

Hay quienes sugieren que el final del código esta próximo. Que los programadores ya no serán necesarios por que los empresarios generarán programas a partir de especificaciones
- No es cierto. El código nunca desaparecerá ya que representa los detalles de los requisitos. En ningún nivel, dichos detalles no se pueden ignorar ni abstraer, deben especificarse y para especificar requisitos de forma que un equipo pueda ejecutarlos se necesita la programación
- Esperan descubrir una forma de crear maquinas que hagan lo que queramos en lugar de lo le digamos. Esas maquinas tendrían que entendernos de tal forma que puedan traducir las necesidades ambiguas en programas perfectamente ejecutados que satisfagas dichas necesidades a la perfección
- Esto no sucederá. Ni siquiera los humanos con toda su intuición y creatividad han sido capaces de crear sistemas satisfactorios a partir de las sensaciones de sus clientes
- La disciplina de requisitos nos ha enseñado que los requisitos bien especificados son tan formales como el código y que pueden actuar como pruebas ejecutables de dicho código
### Código incorrecto

- Prologo del libro *Implementation Pattern* de Kent Beck, afirma esta frágil premisa *El código correcto es relevante*
- El código correcto es relevante por que durante mucho tiempo hemos tenido que sufrir su ausencia
- Todos hemos sentido alivio de ver como un programa incorrecto funcionaba y hemos decidido que un mal programa que funciona es mejor que nada. Todos hemos dichos que lo solucionaríamos después. Evidentemente por que aquel entonces no conocíamos la ley de LeBlanc: *Después es igual que nada*
### El coste total de un desastre

El grado de sufrimiento puede ser significativo. En un periodo de un año o dos, los equipos que avancen rápidamente al inicio de un proyecto pueden acabar a paso de tortuga. Cada cambio en el código afecta a dos o tres partes del mismo. Ningún cambio es trivial

Para ampliar o modificar el sistema es necesario comprender todos los detalles, efectos y consecuencias, para de este modo poder añadir nuevos detalles, efectos y consecuencias. Con el tiempo el desastre aumenta de tal modo que no se puede remediar

Al aumentar el desastre, la productividad del equipo disminuye y acaba por desaparecer. Al reducirse la productividad, el director hace lo único que puede: ampliar la plantilla del proyecto con la esperanza de aumentar la productividad. Pero esa nueva plantilla no conoce el diseño del sistema. No conocen un la diferencia entre un cambio adecuado al objetivo de diseño y otro que lo destroce. Por lo tanto, todos se encuentran sometidos a una gran presión para aumentar la productividad. Por ello cometen mas errores, aumenta el desastre y la productividad se acerca a cero cada vez mas

### El enigma

No se cumple un plazo de entrega cometiendo un error. De hecho, el error nos ralentiza de forma inmediata y hace que no lleguemos al plazo de entrega. La única forma de avanzar es intentar que el código siempre sea limpio

- Pero como crear código limpio. No tiene sentido intentar crearlo si no sabe lo que es

### Concepto de código limpio

Según Bjarne Stroustrup inventor de C++:

*Me gusta que el código sea elegante y eficaz. La lógica debe ser directa para evitar errores ocultos, las dependencias deben ser mínimas para facilitar el mantenimiento, el procesamiento de errores completo y sujeto a una estrategia articulada, y el rendimiento debe ser optimo para que los usuarios no tiendan a estropear el código con optimizaciones sin sentido. El código limpio hace bien una cosa*

Según Grady Booch, autor de *Object Oriented Analysis and Design with Applications*:

*El código limpio es simple y directo. El código limpio se lee como un texto bien escrito. El código limpio no oculta la intención del diseñador, sino que muestra nítidas abstracciones y lineas directas de control*

Según David Thomas, fundador de OTI, el padrino de la estrategia Eclipse:

*El código limpio se puede leer y mejorar por parte de un programador que no se su autor original. Tiene pruebas de unidad y de aceptación. Tiene nombres con sentido. Ofrece una y no varias formas de hacer algo. Sus dependencias son mínimas, se definen de forma explicita y ofrece una API clara y mínima. El código debe ser oculto en función del lenguaje, ya que no toda la información necesaria se puede expresar de forma clara en el código*

### Somos autores

Los autores son responsables de comunicarse correctamente con sus lectores. La próxima vez que escriba una linea de código, recuerde que es un autor y que escribe para sus lectores juzguen su esfuerzo.

En realidad la proporcion de tiempo entre tiempo dedicado a leer frente a tiempo dedicado a escribir es de mas de 10:1. Constantemente tenemos que leer código antiguo como parte del esfuerzo de crear nuevo código

Al ser una proporción tan elevada, queremos que la lectura código sea sencilla aunque eso complique su creación. 
### Regla del Boy Scout

No basta escribir código correctamente. El código debe limpiarse con el tiempo.
Los Boy Scouts norteamericanos tienen una regla sencilla que podemos aplicar a nuestra profesión

*Dejar el campamento mas limpio de lo que se ha encontrado*

No hace falta que la limpieza sea masiva.
- Cambie el nombre de una variable
- Divida una función demasiado extensa
- Elimine elementos duplicados
- Simplifique una instrucción if compuesta
